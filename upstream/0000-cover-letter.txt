Subject: [PATCH] Input: xpad - add GameSir G7 Pro IMU and battery support

The wired GameSir G7 Pro (3537:109b) already works as a gamepad through
xpad, but its raw 6-axis IMU and battery are only available in vendor
report 0x10 on the same interface.  GameSir Nexus and the controller's
firmware only map gyro to a stick or mouse, so SDL3, Eden and ScarletNX
never see an SDL_SENSOR_GYRO source.

Extend xpad for this VID/PID instead of adding a separate driver.  A
separate driver cannot bind reliably: USB driver matching is
registration-order based, xpad's GameSir match is vendor-wide, and
already-bound devices are skipped.  Keeping the support in xpad also
keeps the existing gamepad and FF paths untouched.

The patch:

- sends the vendor heartbeat (0f 00 seq 02 f2) on interrupt endpoint
  0x02 from a delayed work,
- parses report 0x10 only for 3537:109b/100a,
- registers a second input device, "... Motion Sensors", following
  hid-playstation: INPUT_PROP_ACCELEROMETER, ABS_X/Y/Z (accel),
  ABS_RX/RY/RZ (gyro), MSC_TIMESTAMP, resolution 8192/g and
  16/(deg/s), and the same uniq as the gamepad so SDL3 pairs them,
- exposes battery capacity/status through power_supply,
- leaves the existing xpad gamepad reports and FF_RUMBLE path in place.

Tested on a wired 3537:109b (bcdDevice 0x0240), SDL3 3.4.18:

- `input: GameSir G7 Pro` and `GameSir G7 Pro Motion Sensors`; same
  Uniq=0000377903ED91EB,
- udev: ID_INPUT_JOYSTICK on the gamepad, ID_INPUT_ACCELEROMETER on the
  motion node,
- SDL3: one gamepad, gyro=1 accel=1; stationary accel ~9.8-10.0 m/s^2;
  rotating the controller produced +/-3-5 rad/s gyro,
- power_supply `g7pro-1-16-battery`: capacity 100, status Full,
- `rumble_test: OK`, grip vibration observed,
- hotplug, physical replug (including the 1022 native/GIP recovery via
  Share+Menu), module reload and xpad restore.

Known issues / review requests:

- This touches a widely used driver.  All new paths are behind
  `g7pro_is_device()` (VID 3537, PID 109b/109c/100a); the existing
  report and FF paths are not changed.  I would appreciate guidance on
  whether the PID list should be narrower.
- The vendor packet has separate LT/RT motor percentages.  Generic
  FF_RUMBLE only carries strong/weak, so the existing xpad FF path
  drives the grips; trigger channels are left at zero.
- xpad is currently orphaned.  I am not asking to become a maintainer;
  I am happy to iterate on review and keep the proof/test harness
  public.
- KASAN/KCSAN/lockdep were not available on the test host (KFENCE is
  enabled).  sparse, W=1, checkpatch (apart from the intentional
  missing Signed-off-by) and the parser tests are clean.
